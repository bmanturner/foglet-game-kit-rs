- [x] **4b** — Implement `create_challenge`. Test: starts in `open`. [4a]
      → New `Challenge` read model, `ChallengeState` enum (`Open`/`Accepted`/`Declined`/`Resolved`/`Expired`) with `as_str()` as the single source-of-truth mapping to the schema-level `CHECK` vocabulary, and `ChallengeError` (`EmptyKind`, `Sqlite`, `NotFound { id }`). `WorldDb::create_challenge(challenger, target, kind, stake, expires_at)` uses `INSERT … RETURNING` (same pattern as `send_notice`/`append_event`) so the caller gets the autoincrement id, SQL-side `CURRENT_TIMESTAMP`, and the schema-side `DEFAULT 'open'` in one round-trip. New shared `row_to_challenge` decoder so the `RETURNING` write path and 4c–4f read paths share one column list — a future schema reorder surfaces as a type error rather than a silent field swap. Four behavioural tests pin: `create_challenge_starts_in_open` round-trips through primary-key SELECT and asserts `state == "open"` plus all three transition timestamps + `result` are `None` (a regression that defaulted any of them at insert time would observably flunk), `create_challenge_rejects_empty_kind` pins `EmptyKind` + `COUNT(*) = 0` invariant, `create_challenge_supports_optional_stake_and_deadline` round-trips `None`/`None` as `NULL`/`NULL` (guards against a "helpful default" regression like `stake.unwrap_or("{}")`), and `challenge_state_as_str_matches_schema_vocabulary` pins every variant against the `CHECK` alphabet. - [x] **4c** — Implement `accept_challenge`. Test: `open -> accepted`; accepting expired challenge fails. [4b]
      → New `WorldDb::accept_challenge(id) -> Result<Challenge, ChallengeError>` performs a single conditional `UPDATE … RETURNING` whose `WHERE` clause folds three checks: `id = ?1 AND state = 'open' AND (expires_at IS NULL OR datetime(expires_at) > datetime('now'))`. The success path is one round-trip and natively atomic — same shape as `mark_read` (SPEC §4.2 "transitions MUST be transactional" is satisfied by SQLite's per-statement atomicity for single-statement helpers; the `transaction()` wrapper is reserved for multi-statement helpers like the upcoming market buy). On `QueryReturnedNoRows`, a diagnostic SELECT (`state` plus a SQL-side `deadline_lapsed` flag using the same `datetime()` normalisation as the gate) maps to one of `NotFound` / `Expired` / `InvalidTransition`. The `datetime()` wrapping handles both ISO forms the kit accepts (`'YYYY-MM-DDTHH:MM:SSZ'` from callers, `'YYYY-MM-DD HH:MM:SS'` from `CURRENT_TIMESTAMP`) so the comparison is chronological, not lexicographic. Two new error variants: `InvalidTransition { id, from: String, to: ChallengeState }` (carries actual `from` as a String so a future schema state added without a matching enum variant still surfaces verbatim) and `Expired { id }` (specialisation of the open→accepted block when the deadline has passed but the sweeper hasn't run yet — distinguishing these in the UI is more useful than collapsing them). The diagnostic helper `diagnose_failed_transition` is private and shared so 4d/4e land without copy-paste. Four new tests: happy path (state flips, accepted_at populated, resolved_at/result stay None, primary-key SELECT confirms durability), expired path (typed `Expired` + row-unchanged invariant on state and accepted_at), already-accepted path (typed `InvalidTransition` from `accepted` + accepted_at does not advance on second call), and missing-id path (typed `NotFound`). - [x] **4d** — Implement `decline_challenge`. Test: only `open -> declined` is valid. [4b]

Unlike `accept_challenge`, decline does **not** check `expires_at`: SPEC §4.2's "Expired challenges cannot be accepted" is specifically scoped to acceptance — declining a stale open challenge is legitimate (target sees the lapsed entry in their inbox before the sweeper runs and explicitly says "no thanks"). ### Task 5 — Market listings

- [x] **5a** — Add `market_listings` migration with seller, item key, display name, price, quantity, timestamps, metadata. [Task 1]
      → New `crates/foglet_game/src/market.rs` exports `MARKET_LISTINGS_MIGRATION` (`version = 8`, `create_market_listings`) — third v3 migration, claiming the next slot in the `6+` namespace `docs/shared-world.md` §8.1 reserved (notices=6, challenges=7). Schema mirrors SPEC_v3 §4.3 column-for-column: nullable `seller_player_id`/`expires_at`/`metadata` (SPEC explicitly allows NPC/system listings), `NOT NULL` `item_key`/`display_name`/`price`/`quantity`. Schema-level `CHECK (price >= 0)` and `CHECK (quantity >= 0)` are the safety net for SPEC §4.3's "MUST reject negative prices and negative quantities" — Task 5b's helper does Rust-side validation, but a regression that bypassed the validator (raw-SQL test fixture, future helper that forgot to validate) flunks at INSERT time rather than landing a corrupt row. `price` is `INTEGER` (not `REAL`) because IEEE-754 currency is a known footgun (`0.1 + 0.2 != 0.3`); games that need fractional pricing scale into minor units at the boundary. One partial index ships with the migration: `idx_market_listings_active` over `(created_at, id) WHERE quantity > 0` — exhausted listings fall out of the index automatically the moment a buy commits, so the `active_listings` query (Task 5c) never has to filter them at query time. No `kind` column: `item_key` already serves the "stable machine-readable handle game code dispatches on" role (notices have both because their `kind` is UI-category vs subject-of-mail; listings only have one such handle). Three schema tests pin: table existence + column shape, both CHECK constraints accept zero-and-positive while rejecting negative price and negative quantity (covers all four spec halves), the partial-index `WHERE` clause, and migration idempotency. Re-exported `MARKET_LISTINGS_MIGRATION` from `foglet_game::lib`. Workspace tests rose 730 → 734.
- [x] **5b** — Implement `create_listing`. Test: negative price/quantity rejected. [5a]
